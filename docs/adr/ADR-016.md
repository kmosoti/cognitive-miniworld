# ADR-016 — Declarative scenario and schedule boundary

Status: accepted

## Context

Milestone 0 needs fixtures that can change hidden world conditions without
putting executable callbacks, mutable mappings, or privileged state into an
agent interface. Scheduled changes must also remain deterministic when several
changes share a tick or an action spans more than one tick.

## Decision

Scenario manifests and every nested declaration are frozen, strict
`msgspec.Struct` values with canonical JSON encoding. A manifest includes its
fixed seed set, complete initial world, hidden parameters, preregistered primary
and safety metrics, kill criterion, stimuli, horizon, and typed schedule. Invalid
or oversized input is rejected before a world, worker, or event log is created.

Schedule records are ordered by tick and declaration identity. Two records may
share a tick only when they address different targets; conflicting writes to the
same target at the same tick are invalid. A change takes effect at the beginning
of its tick, before that tick's observation and action, including ticks crossed
inside a multi-tick action. Stimulus randomness uses an independent named stream
`stimulus:<stimulus-id>`.

The public scenario projection exposes capabilities and explicitly visible
stimuli or changes only. Hidden parameters, resource quality, evaluator truth,
and hidden schedule entries remain evaluator-side. Silent sensor degradation
changes the sampling process while leaving the sensor's reported reliability
unchanged, so the fault is not announced through metadata.

## Consequences

Every manifest is self-contained, hashable, replay-identifiable, and safe to
compile repeatedly. Adding a new scheduled effect requires a typed record and a
deterministic target identity; arbitrary callbacks and mapping payloads remain
out of scope. The kernel retains its pure transition boundary while applying
due scenario changes as part of immutable tick advancement.
