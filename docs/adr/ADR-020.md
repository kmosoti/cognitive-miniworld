# ADR-020 — CI tier split and marker-coverage boundary

Status: accepted

## Context

Every quality gate ran in one job through a single bare `pytest` invocation.
That invocation collected every registered marker, so the replay gates from
MW-003 and the fixture and baseline smoke experiments from MW-005 and MW-007
could not escape CI without an explicit workflow change. The convenience was
real but it bundled two different kinds of claim.

The `performance` tier is one test: a relative thread-scaling curve for the
free-threaded interpreter. It measures the runtime and the runner, not the
behavior of this repository, and its verdict depends on how much other work the
machine is doing. It is the only timing-sensitive assertion in the suite, so it
is also the only gate that can fail a correct change. Meanwhile the job carried
a fifteen-minute timeout for work that finishes in seconds, which turns a hung
runner into a quarter hour of waiting rather than a fast, obvious failure.

## Decision

The pull-request path runs `pytest -m "not performance"`. The `performance`
tier moves to its own job that runs `pytest -m performance` on pushes to `main`,
on a nightly schedule, and on manual dispatch. Contributors are gated on
correctness; the environment claim is re-measured on a cadence and on the
integration branch, where a regression still blocks before release rather than
before review. The concurrency group is keyed by event name as well as ref so a
scheduled run cannot cancel an in-progress push build.

Splitting tiers gives up the "one invocation collects everything" guarantee, so
a compensating proof replaces it. Every job that runs pytest sets
`CMW_COLLECTED_OUT`; a `pytest_collection_finish` hook in `tests/conftest.py`
writes the node ids that invocation actually selected, and each job uploads that
manifest. A final `coverage` job unions the manifests and compares them against
an unfiltered collection of the whole suite, failing with the node ids that no
invocation collects. The `performance` job therefore runs on every event: on a
pull request it collects without executing, so the proof stays complete while a
timing measurement of the runner still cannot block review.

This is deliberately a dynamic check rather than a static one. The first
implementation was static: it read the markers registered in `pyproject.toml`,
parsed the pytest invocations out of the workflow, and evaluated the marker
expressions itself. That required reimplementing three things it did not own --
YAML scalar folding, shell word-splitting, and pytest's own marker resolution --
and review found six ways to fool it: a step merely *named* `pytest ...`, an
`echo pytest`, a folded `>` block, singleton-marker semantics against a test
carrying two markers, class-level marks, the attached `-mexpr` option form, and
`pytest.param(marks=...)`. Each was fixed and tested, and the file grew from 63
lines to 374. The pattern, not any individual hole, is the argument: an
approximation of someone else's parser accumulates gaps indefinitely. Unioning
what pytest itself reports cannot drift from what pytest does, and it names the
uncovered test rather than the uncovered marker.

Job timeouts drop from fifteen minutes to five for the correctness jobs. The
performance job gets ten, because its assertion is a timing measurement and
needs headroom on a contended runner without granting a hang a long silence.

## Rejected: pytest-xdist

Parallelizing the suite with `pytest-xdist` was considered and is rejected for
now. After the M0 optimization work removed the quadratic manifest validation the pull-request
selection runs in roughly thirteen seconds, so the available saving does not
justify a dependency. `pytest-xdist` is not on the approved list; adding it would require
its own ADR and Kennedy's sign-off. Its `--dist load` scheduling assigns tests
to workers nondeterministically, which would mask order-dependence rather than
expose it, and this project treats reproducible ordering as a first-class
property. Hard invariant 8 confines concurrency to isolated
`(scenario, seed, variant)` runs; a test-level work-stealing scheduler is a
different concurrency model than the one the invariants describe. Finally, the
`performance` gate's timings are meaningless when co-scheduled with other tests,
so the one tier that might benefit from more machine is the tier that parallel
execution would invalidate. Revisit if the suite exceeds roughly sixty seconds.

## Rejected: shrinking the scaling gate's constants

Reducing `TASK_ITERATIONS` from 1,500,000 to 400,000 and `TIMING_SAMPLES` from
5 to 3 was implemented, measured, and then reverted. Two things were argued for
it, and both were wrong.

The first was an inference: the gate's verdict is a pairwise ratio test on the
per-worker medians and names neither constant, so -- it was claimed -- the
reduction could not change which programs pass, only the variance of the
estimate. That does not follow. The decision rule is a function of the medians
it is given, and the constants determine those medians; changing them changes
the inputs, not the rule. The conclusion is retracted.

The second was measurement: a fifteen-trial study per configuration on a
twelve-core development machine found worst-case step margins of 25.2% at
400k x 3 against 23.5% at the original 1.5M x 5, with no failures in either.

That study did not generalize to the hardware CI actually runs on. GitHub's
standard runners have four vCPUs, so `worker_levels` includes 4 and the gate
measures a four-worker probe on a four-CPU machine already hosting the runner
agent. At 400,000 iterations a probe takes about 0.14s, short enough that pool
startup and runner contention dominate the 2-to-4 step. Run 33137139162 failed
exactly there: 1 worker 0.279s, 2 workers 0.141s, 4 workers 0.147s -- a 49%
improvement followed by a 4% regression. The longer probe amortizes that
overhead, which is why the original constants have passed on this hardware
consistently.

The decision is therefore to keep the original constants. Once the tier split
above moves this gate off the pull-request path, the reduction's only remaining
benefit is roughly thirteen seconds on a job that blocks nobody, bought at the
cost of a demonstrated failure on the exact machines CI uses. A margin measured
on a developer's twelve-core box is not evidence about a four-vCPU runner, and
this gate exists to make a claim about the runner.

## Consequences

A pull request no longer proves the free-threaded scaling curve, and a scaling
regression is caught on `main` or overnight instead of at review time. In
exchange, review feedback is faster and cannot be blocked by runner contention.
Adding a new test tier now costs a workflow edit: a test that no job collects
fails the `coverage` job by name until some job claims it. The cost of the proof
is one extra job and an artifact round-trip, and the `performance` job now
appears on pull requests as a collection-only run. In exchange the check has no
parser of its own to keep correct, and it verifies the invocations that actually
ran rather than the workflow text that describes them.
