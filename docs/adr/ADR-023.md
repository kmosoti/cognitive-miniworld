# ADR-023 — Positive-support affordance generation and coverage gate

**Status:** accepted · **Date:** 2026-08-28 · **Source:** MW-013

## Context

MW-013 must exclude actions contradicted by observable evidence without turning
missing evidence into a false negative. It must also preserve parallel
candidates and make a generator failure distinguishable from a later
arbitrator's failure to choose. The frozen `BeliefState` and `ActionProposal`
contracts already carry the needed hypotheses, preconditions, provenance, and
uncertainty, so no contract revision is needed.

## Decision

The first affordance generator is finite and declarative. Each sorted action
template names up to 16 boolean observable preconditions and carries at most
64 action parameters. Parameter validation and proposal construction are
charged to the bounded-work gate. A template is emitted iff its precondition
conjunction has positive posterior support: `False`
contradicts a precondition, `True` confirms it, and a missing feature remains
possible but unconfirmed. Non-boolean values at named preconditions are
rejected. Proposal uncertainty bounds are the confirmed and possible posterior
mass; confidence is the lesser of belief confidence and confirmed mass. The
generator examines at most 64 templates, 256 hypotheses, and 10,000 belief
source-event IDs with an explicit bounded-work gate. Repeated provenance copies
are charged once per template before any proposal is constructed.

Generation returns both proposals and rejected template IDs. A separate cycle
observation reports `generation_failed` only when no proposals exist and
`selection_failed` only when proposals exist but no proposal ID was selected.
It observes selection but never performs it; reusable arbitration remains
reserved for MW-014.

The confirmatory evaluator crosses all `2^3` hidden truth assignments with all
`2^3` public observation masks for `exit_clear`, `resource_present`, and
`shelter_visible`, using a named RNG stream only to rotate complete case order.
Across benchmark seeds 1000–1099, feasible-best-action recall must be `1.0`,
must beat a consume-only goal baseline, invalid-action rate must improve over
enumerating every action by at least `0.1`, and every incomplete case must retain
at least two candidates. Separate generation- and selection-failure fixtures
must both be observed.

## Consequences

Incomplete observations increase uncertainty and candidate-set size instead of
silently deleting feasible actions. The evaluator may know hidden feasibility,
but agent code receives only public beliefs. Extending preconditions beyond
boolean conjunctions, changing the support rule or thresholds, or allowing the
generator to select an action requires a new decision record.
